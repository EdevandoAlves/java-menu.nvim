1. INTRODUCTION                                                *java-menu-intro*

java-menu.nvim is a contextual menu layer for Java development in Neovim.
Eight groups — New, Generate, Refactor, Imports, Build/Run, Tests,
Debug, Project — collect the operations you need for the current situation,
and every entry says whether it is available and, when it is not, why.

The Java work itself is done by |jc.nvim| and by the jdtls language server
you already run. java-menu.nvim never starts, installs or manages a language
server. It organizes existing capabilities, adds a preview-and-apply
workflow for WorkspaceEdit refactorings (|java-menu-preview|) and a guided
Change Signature menu, and stays out of the way otherwise.

It is complementary to jc.nvim, not a replacement. If you prefer driving
jc.nvim's commands and mappings directly, you may not need this plugin.

Menus work from Java sources, `pom.xml`, `build.gradle(.kts)` and any buffer
inside a Java project; they are not gated on |filetype| alone.

==============================================================================
2. REQUIREMENTS                                            *java-menu-requirements*

- jc.nvim (https://github.com/artur-shaik/jc.nvim) — required. `setup()`
  fails with a clear error when it is missing.
- A running jdtls, started by your own configuration (nvim-jdtls, nvim-java
  or lspconfig) — required for semantic operations (Generate, Refactor,
  Imports, run-main classpath, Tests, Debug). New and Build/Run work
  without it. java-menu.nvim detects whichever client is already attached
  to the buffer.
- Optional: snacks.nvim (pickers; falls back to `vim.ui.select`/
  `vim.ui.input`), which-key.nvim (group label), neotest (Tests menu,
  via jc.nvim's adapter), nvim-dap + java-debug bundle (Debug menu),
  Maven or Gradle (Build/Run; `mvnw`/`gradlew` preferred when executable),
  `curl` (or `wget`) and `unzip` (Spring Boot project creation via Spring
  Initializr; `curl`/`wget` also enables optional Maven Central search —
  Plain Java, Maven creation and manual Maven dependency entry work offline).

Developed and tested on Neovim 0.12, Linux. The practical Neovim floor is
the one jc.nvim itself requires; older versions are untested.

java-menu.nvim never downloads, installs, bundles, or updates jc.nvim,
jdtls, optional plugins, or build tools. You install and manage them
yourself; java-menu.nvim only detects what is present and reports clear
errors or disabled reasons when something is missing or incompatible.

3. INSTALLATION                                              *java-menu-install*

Install with lazy.nvim. Declare jc.nvim as its own spec (java-menu's
`setup()` needs it loaded at startup): >lua

  {
    "artur-shaik/jc.nvim",
    lazy = false,
    ft = { "java" },
    opts = { keys_prefix = "<leader>j", default_mappings = false },
  },
  {
    "EdevandoAlves/java-menu.nvim", -- GitHub
    main = "java_menu",
    lazy = false,
    opts = { prefix = "<leader>j" },
    dependencies = { "artur-shaik/jc.nvim" },
  }
<
Installing from a local checkout instead? Point `dir` at your clone and
keep everything else the same: >lua

  {
    dir = "~/path/to/java-menu.nvim", -- your local clone
    name = "java-menu.nvim",
    main = "java_menu",
    lazy = false,
    opts = { prefix = "<leader>j" },
    dependencies = { "artur-shaik/jc.nvim" },
  }
<
Declaring jc.nvim only as an inline `dependencies` entry without a spec of
its own does not work: lazy.nvim then loads it too late and `setup()` fails
with its missing-dependency error.

Then generate help tags: >vim

  :helptags ALL
<
When jc.nvim is missing, `setup()` fails with an error naming the missing
dependency instead of half-registering menus.

4. SETUP                                                        *java-menu-setup*
                                                              *java-menu-opts*
                                                        *java-menu-configure*
>lua
  require("java_menu").setup({
    prefix = "<leader>j", -- keymap prefix
    groups = {            -- enable/disable groups (default: all enabled)
      new = true,
      generate = true,
      refactor = true,
      imports = true,
      build = true,
      tests = true,
      debug = true,
      project = true,
    },
    which_key = true,     -- label the group in which-key when installed
  })
<
                                                                *java-menu-trigger*
`require("java_menu").trigger(name)` runs one group on demand (name is one
of the group keys above) — useful for lazy-loading a single menu from your
own key specs.

Behavior you get without asking:
- `setup()` is idempotent: re-running it removes its own keymaps and
  command first, then re-registers. Nothing is duplicated.
- Existing keymaps are respected: a conflicting mapping is kept, the
  java-menu one is skipped, and the conflict is reported with the exact
  key.
- No Java module is loaded by `setup()`; each keymap requires its module
  on first use.

5. COMMANDS                                                  *java-menu-commands*
                                                            *java-menu-javamenu*
                                                              *java-menu-trigger-cmd*
`:JavaMenu [group]` ~
Opens one of the eight menus, with command-line completion for
`new | generate | refactor | imports | build | tests | debug | project`.
Without an argument it lists the accepted groups.

6. KEYMAPS                                                    *java-menu-keymaps*

Global keymaps registered by `setup()`; `<prefix>` is the `prefix` option
(default `<leader>j`).

|Mode|  Key             | Action                    | Requirements             |
|-----|------------------|---------------------------|--------------------------|
|n    | `<prefix>n`      | New                       | basic creation needs no jdtls |
|n    | `<prefix>g`      | Generate                  | one jdtls client         |
|n/x  | `<prefix>r`      | Refactor                  | jdtls for most entries   |
|n    | `<prefix>i`      | Imports                   | jdtls attached           |
|n    | `<prefix>b`      | Build / Run               | Maven or Gradle          |
|n    | `<prefix>t`      | Tests                     | neotest + jdtls          |
|n    | `<prefix>d`      | Debug                     | nvim-dap + java-debug    |
|n    | `<prefix>p`      | Project                   | no jdtls needed          |

Keymap conflicts with mappings that are not java-menu's are never
overwritten: yours is kept, ours is skipped, and the conflict is reported.

7. MENU GROUPS                                                  *java-menu-groups*
                                                                *java-menu-new*
New ~
Wizard for Class, Abstract Class, Interface, Enum, Record, Annotation,
Exception, Class with main, Singleton, Serializable and jc.nvim's template
library (JUnit 5, Spring stereotypes, JPA entity, ...). Project-aware
source root, package and module resolution; `extends`/`implements` search
through jdtls when attached; JUnit/Spring/JPA availability detected from
the build file. Basic class creation works without jdtls.

                                                              *java-menu-generate*
Generate ~
Constructor (Select Fields), All-Args Constructor and No-Args Constructor,
getters/setters, `toString()`, `hashCode()`/`equals()`, unimplemented
abstract methods — via jc.nvim, with duplicate detection (an existing
equivalent is offered for reuse/replacement instead of appended blindly).
All-Args uses jdtls' eligible field list without opening a picker; No-Args
reuses the previous Default Constructor implementation and is blocked when
a final field still requires initialization.

                                                              *java-menu-refactor*
Refactor ~
Extract variable (also all occurrences), extract constant, extract method
(visual mode), static import (also enum constants), flip call arguments,
rename symbol, move class, change signature. Rename, Move Class and Change
Signature results go through the preview workflow (|java-menu-preview|).
Rename Package and Move Package appear in the menu but are permanently
disabled: current jdtls offers no supported path for them.

                                                               *java-menu-imports*
Imports ~
Organize (smart, remembering your choices via jc.nvim), organize with
candidate choice, add missing, remove unused, organize without reordering,
replace import (pick among same-named types), import style presets,
expand wildcard imports.

                                                                  *java-menu-build*
Build / Run ~
Run a main class (classpath from jdtls), run a Spring Boot application,
compile, package, clean, install, or pick a custom goal. Detects
`mvnw`/`mvn`/`gradlew`/`gradle` (wrapper preferred), runs from the reactor
root, scopes Maven with `-pl <module> -am` and Gradle with
`:module:task`. Output goes to a dedicated buffer. One build process runs
at a time: starting another build — including Repeat — is refused until
you stop. Repeat/Stop/Output are keyed by project root, and stopping a
process that belongs to another project asks "keep / terminate" first.
Run Settings stores JVM and application arguments per project and offers
Spring profiles discovered from application-* files. Restart Last Process
relaunches the project's recorded command. Run Main and Spring load the
project-root .env by default when present; toggle it in Run Settings.
The parser accepts simple KEY=VALUE lines without shell execution. Captured
output redacts literal values and selected URL-encoded or JSON-escaped forms
of values at least six bytes long. Redaction cannot guarantee protection from
arbitrary transformations or fragments split across lines or streams; short
values can redact ordinary output. Arguments are stored locally: put secrets
in .env instead.
Output lines longer than 64 KiB are truncated and the remainder is suppressed
until the next newline. Captured process output is limited to 4 MiB per run.
Partial lines can be delayed until newline or exit.
Background groups left after normal exit remain tracked for Stop; Restart
waits for verified groups in the same project to exit. If group identity
cannot be verified, Java Menu avoids sending signals and blocks automatic
restart until the group exits or is stopped manually. Verification depends on
operating-system process information and may be unavailable outside Linux. Repeat Last uses Java Menu's own canonical-root history only and
neither reads nor writes jc.nvim's `build-last` (`JCbuildLast`), as
jc.settings uses non-injective path keys without cross-session ownership.
Short .env values may cause unrelated arguments to be excluded from saved
history. Previously saved build histories and run settings without project
ownership metadata (including legacy unhashed settings files) are neither
imported nor deleted; run a build or re-save in Run Settings to create
scoped data.

                                                                  *java-menu-tests*
Tests ~
Run nearest/file/suite/pick through neotest with jc.nvim's adapter
(classpath from jdtls), re-run last, stop, summary/output, optional
precompile, and navigate in either direction between a class and its test.
Matches prefer the current module and support *Test, *Tests, *IT and Test*
names. Ambiguous matches are offered for selection; a missing test can be
created after confirmation. The test picker prioritizes the current module
and package. Open a project file before using the menu from an output buffer.
Without neotest the menu says so instead of breaking.

                                                                  *java-menu-debug*
Debug ~
Debug a main class (only launch configs of the current project are
offered; ambiguous ones are flagged), debug nearest/class JUnit test via
jdtls' java-test, attach to a running JVM, toggle/conditional breakpoints
and session controls — through nvim-dap and the java-debug bundle.

                                                                *java-menu-project*
Project ~
Project-level actions, available even in an empty directory and without
jdtls. Four entries:
  New Project...    Wizard for Plain Java, Maven and Spring Boot projects.
                    Nothing is written before the final confirmation;
                    cancelling at any step creates nothing. Generation or
                    extraction is staged in a hidden sibling directory and
                    published by atomic rename (entry-by-entry into an
                    already-empty target); rollback removes only what was
                    created, an existing destination is never overwritten
                    (empty ones are reused) and symlinks are refused.
                    Plain and Maven work offline: Maven writes a minimal
                    deterministic pom.xml (maven.compiler.release, zero
                    dependencies) plus Main.java, resources and test dirs;
                    plain writes Main.java only. Main.java prints
                    "Hello from <name>!" — jc.nvim's main template is used
                    when it satisfies that contract, but v1.7.0 renders an
                    empty body, so a built-in generator is used in practice.
                    Spring Boot queries Spring Initializr (requires network,
                    `curl` or `wget`, and `unzip`; disabled with a checked
                    reason when tools are missing), lets you pick build
                    type, Boot version, packaging, Java version, coordinates
                    and optional dependencies, validates the zip listing
                    before extraction (rejecting `..`, absolute/drive paths,
                    symlinks and non-file/non-dir entries), re-checks the
                    extracted tree before publishing, and offers Retry or
                    Cancel on network errors without leaving partial files.
                    Opens Main.java (plain/Maven) or pom.xml/build.gradle*
                    (Spring Boot), reports the full path and a compile/run
                    hint. No cwd change, no jdtls start, no git init, no
                    scripts.
  Project Info...   Read-only buffer (q closes): root, build tool (Maven |
                    Gradle | Plain Java (no build file)), modules (count +
                    relpaths), source roots, Gradle discovery limitation,
                    jdtls attached (workspace dir) or not. Enabled when a
                    build file or a src/main/java directory is found above
                    the buffer.
  Dependencies...   Enabled in Maven or Gradle projects (multi-module
                    projects pick the module first, current module on top).
                    - List dependencies...: read-only report (q closes).
                      Maven lists project-level dependencies with managed-version
                      provenance, declared <parent>, exact <dependencyManagement>
                      entries, explicit unresolved <parent>/BOM-import caveats,
                      and conditional <profiles> context (IDs, unevaluated
                      <activation>, profile <dependencyManagement> and
                      dependencies). Gradle
                      performs a static read-only parse of Groovy
                      build.gradle and Kotlin DSL build.gradle.kts literal
                      entries plus gradle/libs.versions.toml, and reports
                      dynamic, interpolated, helper or scoped forms as
                      partial notes without executing Gradle.
                    - Add dependency...: optional Maven Central search or
                      offline manual entry. Maven respects exact local
                      dependencyManagement and notes unresolved parent/BOM
                      coverage. Gradle inserts literal coordinates in a
                      conservative Groovy/Kotlin subset; version catalogs
                      remain unchanged and ambiguous forms are refused. Both
                      check duplicates and unsaved buffers, show confirmation,
                      preserve comments and permissions, and request per-buffer
                      JDTLS sync when attached.
                    - Open build file: opens pom.xml / build.gradle(.kts).
                    - Sync JDTLS: re-imports the build file on the buffer's
                      attached JDTLS client (disabled when not attached).
  Environment...    Read-only buffer (q closes): Neovim version, java/javac,
                    JAVA_HOME, Maven/Gradle, curl/wget and unzip, wrappers,
                    jdtls attached (client count + workspace dir) or not
                    (never started), jc.nvim available / MISSING (required),
                    and optional snacks/which-key/neotest/nvim-dap with
                    consequences. Strictly informative: installs, fixes and
                    builds nothing.

8. WORKSPACEEDIT PREVIEW                                     *java-menu-preview*

Rename, Move Class and Change Signature do not write immediately. jdtls
computes a WorkspaceEdit; java-menu.nvim normalizes it into an ordered
plan and shows a review menu listing every affected file. Selecting a file
opens a diff view. From there:

- Apply: performs the file operations (renames, creates, deletes go to
  disk) and applies the text edits into your buffers. Buffers are never
  saved for you — run `:wa` (or save what you want) afterwards.
- Cancel: aborts with nothing changed.

Before applying, the plan is revalidated: buffers with unsaved
modifications to affected files block the apply, and a file that changed
on disk since the preview opened makes the operation refuse. Path-based
operations cannot atomically verify source contents or pin parent directories:
concurrent writes or directory replacements in the final instant can still
cause conflicts. Renames are refused when a no-overwrite operation is
unavailable.

Change Signature reads the method signature from jdtls
(`java/getChangeSignatureInfo`) and lets you reorder/edit parameters,
rename the method, change visibility and return type, and optionally
generate delegate methods.

9. LIMITATIONS                                              *java-menu-limitations*

- jc.nvim Lua surface: a few operations call jc.nvim functions outside its
  documented command/mapping surface — some explicitly internal
  (`_filter_type_symbols`, `_prioritize_types`, `_set_import`, used by
  Replace Import's candidate filtering), others plain module functions
  (per-project import-style storage, the busy check). All are
  contract-checked at runtime: when one is missing, throws, or changes
  shape, the operation is disabled (or falls back safely) with a clear
  reason instead of half-applied.
  The tested baseline is jc.nvim v1.7.0 (pinned commit
  0aaf5bbc07ed1a69d66779187d48bfea6ec863b6); no other version is promised.
  CI runs only the headless FAST suite (no live jdtls, neotest or nvim-dap)
  against that pinned baseline and upstream `main` as an early change
  detector; live jdtls integration specs run locally only.
- Multiple jdtls clients: operations jc.nvim resolves against one global
  client are blocked with an explanatory reason while more than one
  client is attached — Generate, every Imports entry except Replace
  Import, and Extract Variable / Extract Method / Static Import.
  Rename, Move Class, Change Signature and Replace Import keep working
  per buffer.
- Gradle discovery is static: nested modules come from parsing
  `settings.gradle(.kts)` includes and explicit `projectDir` entries.
  Dynamic declarations produce a partial-result note instead of invented
  modules. Real Gradle multi-module task execution (`build_gradle_real_spec`)
  runs when `gradle` is on PATH and skips cleanly when absent; Maven
  execution is tested for real when `mvn` is available.
- Plain Java projects have no build file: Build/Run does not apply, and the
  Java release entered in the wizard is informational only — nothing records
  it. Project Info detects them through a src/main/java directory.
- Generated Main.java uses a built-in generator today: jc.nvim's main
  template (used automatically when it satisfies the contract) renders an
  empty body in v1.7.0.
- Spring Boot creation requires network access to Spring Initializr plus
  `curl` (or `wget`) and `unzip` on PATH; no local version matrix is
  bundled. Network errors offer Retry or Cancel and leave no partial files.
- Dependencies: Maven edits are surgical text insertions (no XML parser);
  textual <parent>/BOM detection cannot prove per-artifact version coverage
  and notes this explicitly when <version> is omitted without an exact local
  <dependencyManagement> match. Maven <profiles> declarations are listed as
  conditional without evaluating activation, and ${...} properties are not
  evaluated. Gradle inspection and conservative editing are static: dynamic
  or ambiguous forms are refused for editing, catalogs are not edited and
  Gradle is not run. Files are rechecked before replacement, but path-based
  APIs cannot guarantee conflict-free replacement against an uncooperative
  concurrent writer in the final instant.
- Project creation runs no git init and installs/configures no tools.
- Rename Package / Move Package are disabled (see |java-menu-refactor|).
- Tested on Linux only; no Windows/macOS validation.

10. TROUBLESHOOTING                                     *java-menu-troubleshooting*

- `setup()` errors mentioning jc.nvim — install artur-shaik/jc.nvim and
  make sure it loads before java-menu.nvim (see |java-menu-install|).
- A `<prefix>…` key did not register — another mapping owns that key; the
  conflict notice names it. Free the key or change `prefix`.
- Build entries disabled — the menu reason tells you what is missing
  (no `mvnw`/`mvn`/`gradlew`/`gradle`, no project root from this buffer).
- Operations blocked mentioning two jdtls clients — close or stop the
  other project's client, or use one of the per-buffer operations
  (|java-menu-limitations|).
- Generate/Imports say jdtls is not attached — start jdtls your usual way
  and reopen the file; java-menu.nvim detects the client when it attaches.
- Help tags missing — run `:helptags ALL` after installing/updating.
